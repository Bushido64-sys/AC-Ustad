THE APP IN ONE LINE
--------------------------------------------------------------------------------
A field technician opens it when an AC or solar inverter shows a code (E6, F4,
"Error 200", a blinking LED) and needs what it means and what to do about it, in
English or Roman Urdu, fully offline, with no signal and no account.

DECIDIONS - LOCKED. Do not re-litigate, do not "improve" these.

IDENTITY
  - App name "AC Ustad", package com.acustad.app, Kotlin + Compose, minSdk 26.
  - A code's identity is (brand, series, code) -> the `uid` column, "brand/series/code".
    NEVER key anything on the code string alone.
  - 1715 of 2139 code strings exist on exactly one brand, but E1 is on 20 brands,
    E3 on 21, E6 on 16, F4 on 15, and 359 code strings are shared.

SEARCH - the feature that makes this app trustworthy
  - Strictly scoped per level, and there is NO global code search:
      Home      -> AC or Inverter          (no search box)
      Brands    -> searches BRAND NAMES only
      Model lines-> searches MODEL NAMES only
      Codes     -> searches CODES IN THAT SERIES only
  - 2139/2139 code strings can be looked up exactly. Showing a technician two
    brands' meanings for "E6" and making them guess is a bug, not a feature.
  - Two search jobs, never mixed: exact/prefix code lookup via the `aliases`
    table (0.2 ms, no crash surface); free-text description via `code_fts`.
  - NEVER pass raw user input to an FTS MATCH - 454 of the 2139 code strings
    throw that way (BLINK-RUNNING -> "no such column: RUNNING"; ";" and "+" ->
    syntax error). Quote the input. Full rule in PHASE_5_SEARCH.md §3.
  - Because brand/model names are searched at every level, the final collapsed
    state must be an EXPANDABLE LIST, never a horizontal chip carousel: a
    carousel hides 45 of the 62 brands behind a swipe nobody performs while
    wearing gloves. It is also the biggest anti-slop trap in this app.
  - Result cap 60 rows per screen, sorted by count desc, then a/c.

DATA
  - The database is READ-ONLY. `favourites` is the only writable table.
  - Favourites are keyed on `code_uid` (never `code_id`) so they survive a
    database swap, and the row copies brand/series/code/titles so the list
    renders with no queries.
  - Every fault code has >=2 causes and >=2 fix steps in both languages.
    Never invent, shorten or paraphrase content (RULE 1).

DESIGN - neo-brutalist chrome + clean readable body text
  - TWO colours only: BLUE (structure) and the SIGNAL hue (alerts/severity).
    Neutrals are blue-tinted, never pure grey, never pure black.
      blue #1668A8  primary button / selected - the ONLY blue that takes white
                     text (5.87:1)
      blue #6FB4DE  light blue accent/border/fill. WHITE TEXT HERE IS 2.27:1 AND
                     FAILS - use ink #0B1F2A on it (7.45:1)
      dark canvas    #0B1116 blue-black, NOT #000000
  - Severity is one hue at five steps AND always a word: DANGER, STOP, CHECK,
    CLEARS, INFO. 60% of faults are STOP, so colour cannot be the signal (RULE 8).
  - 2dp ink borders, corner radius 0-4dp, hard shadow 3dp 3dp 0 on primary
    actions and the selected state ONLY. No pills, no blur, no glass.
  - IBM Plex Sans (prose) + IBM Plex Mono (codes, model names, counts) +
    IBM Plex Sans Condensed (section headers only). Bundled, never substituted.
  - Exactly FIVE icons: back, search, star, external link, expand. No decorative
    iconography, no emoji, no brand logos, no images of any kind.
  - BANNED as generic-AI slop: purple/indigo, Inter/Roboto, grey-400/500 body
    text, three identical cards in a row, icon-in-rounded-square, soft shadow on
    every card, large radii, "Get Started"/"Elevate" copy, a floating pill above a
    heading. Read RULES.md RULE 10 before the first screen and again before
    shipping.
  - Both light AND dark themes, hand-built from design_tokens.xml. Dynamic colour
    is not enabled (it would overwrite the palette on Android 12+).
  - 16sp minimum body, 24sp minimum line height (Roman Urdu needs the room),
    48dp minimum touch targets, 56dp list rows.
  - FIX-STEPS-FIRST order on the detail screen: severity + meaning, then the
    numbered fix steps, then causes, then notes, then source. Steps are numbered
    1..n because "try step 2" is what gets said on the phone.

LANGUAGE
  - The EN / UR switch is a CONTENT switch, not a UI translation. It switches
    code title, meaning, causes, solutions, notes and the severity/confidence
    words. UI labels, BRAND names and MODEL names stay English, because a
    technician reads those in English anyway. There is no values-ur strings file
    and no Urdu script anywhere.

PRIVACY / PERMISSIONS
  - ZERO runtime permissions, ZERO network calls, no analytics, no crash
    reporting, no accounts, no sharing intents. Enforced by CI_CD.md gates.
  - Offline is the only mode: there is no online state, so no offline banner and
    no "update data" button. A data update ships as a new APK version.

WORKING RULES
  - Terminal only. NO EMULATOR, ever - the human installs the APK on a physical
    phone. GitHub Actions builds a debug APK on every push.
  - Build the 9 phases in order, one commit per phase, PROGRESS.md updated in the
    same commit. Message format in RULES.md RULE 20.
  - If the guide and the database ever disagree, THE DATABASE WINS - and say so
    in the report instead of quietly working around it.
